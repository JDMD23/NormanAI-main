# Study: RapidFuzz

- **Repo:** https://github.com/rapidfuzz/RapidFuzz
- **Studied:** 2026-08-06 at commit `03a5137`
- **What it is:** A fast fuzzy string-matching library for Python and C++
  (Levenshtein/Indel-based similarity), a drop-in-ish replacement for
  fuzzywuzzy/thefuzz with a permissive MIT license. C++ core exposed through
  Cython, with a pure-Python fallback and runtime SIMD dispatch.
- **Why it was worth studying:** The collection's clearest specimen of
  **performance engineering behind a stable interface** — how to be fast without
  making speed the user's problem — and the source of two concrete patterns:
  runtime capability dispatch and fallback-with-identical-semantics.

## Architecture at a glance

```
fuzz.py / process.py / distance/*   # public API — thin dispatchers, generated
  ├─ *_cpp.pyx  (Cython → C++ core)  # the fast path
  └─ *_py.py    (pure Python)        # the fallback path, same results
_feature_detector.py                 # AVX2 / SSE2 / none, at runtime
tools/generate_python.py             # the dispatchers are generated, not written
```

## The two headline patterns

### 1. Runtime capability dispatch, behind one import

`fuzz.py` picks the implementation *when it loads*, best-available-first:
AVX2 build → SSE2 build → generic C++ → pure Python, each attempt wrapped in
`suppress(ImportError)` so a missing binary falls through instead of crashing.
An env var (`RAPIDFUZZ_IMPLEMENTATION=python|cpp`) forces a path for
testing/debugging. The caller writes `from rapidfuzz.fuzz import ratio` and gets
the fastest thing that runs *on this CPU, in this install* — SIMD width detected
at runtime, not baked at build.

This is the capability-ladder pattern (Scrapling's fetchers, JustHireMe's
embeddings, brain/09 model tiers) applied to *CPU instruction sets*, with two
sharpening details worth stealing: **best-first with graceful fall-through** (try
the fast path, silently degrade on ImportError — never require the optimal
artifact), and **an escape hatch to pin the tier** for when you need to reproduce
or isolate. The interface is identical across all four tiers; performance varies,
correctness does not.

### 2. The fallback must produce identical results — a semantic contract

`api_differences.md` documents that RapidFuzz "always uses the Indel similarity
both in the pure Python fallback implementation and the C++ based implementation
to provide **consistent matching results**" — explicitly *fixing* a fuzzywuzzy
wart where its Python and accelerated paths gave different answers. The rule:
**a fast path and its fallback are the same function or they are a bug.** A
fallback that quietly returns different results is worse than no fallback,
because it turns "did you compile the extension?" into a silent correctness
variable. This is the multi-implementation conformance idea (jsonschema,
langchain-tests) turned inward: your own two implementations of one interface
owe each other a conformance guarantee, ideally tested by running the same suite
against both (which the `RAPIDFUZZ_IMPLEMENTATION` switch exists to enable).

## What else it does well

- **Generated dispatchers.** `fuzz.py` carries "this file is generated by
  tools/generate_python.py" — the repetitive per-function tier-selection boilerplate
  (which is verbose and error-prone if hand-written across four tiers × a dozen
  functions) is generated from a spec, so the pattern stays consistent and a new
  function can't forget a tier. Codegen used exactly where it earns its keep:
  mechanical, repetitive, correctness-sensitive surface (the checked-generation
  discipline from earlier studies).
- **Honest, precise compatibility docs.** `api_differences.md` enumerates every
  behavioral divergence from the library it replaces, with the *algorithmic
  reason* for each — the drop-in-replacement promise made falsifiable instead of
  marketing. This is how you migrate a userbase off an incumbent without
  Hyrum's-Law surprises (brain/05).
- **The C++ core is independently usable** (header library under `extern/`), so
  the value isn't Python-locked — the domain logic lives below the binding
  (brain/02 dependency direction).
- **Vendored/pinned native build** (CMake, feature-detector as its own compiled
  module with a Python fallback) — even the *feature detector* degrades: if its
  own C++ module fails to import, `supports()` returns False and everything falls
  to scalar/Python. Degradation all the way down.

## Questionable calls and tradeoffs

- **The generated dispatch is verbose and duplicative** in source (the same
  import block repeated per tier and per env-var branch). Generated, so the
  duplication is cheap to maintain — but it reads as a wall, and the generation
  step is a build-time dependency newcomers must understand before editing
  `fuzz.py` (you edit the generator, not the file).
- **Build/packaging complexity is real** — multiple SIMD builds, Cython, CMake,
  per-platform wheels. Justified for a library whose entire value proposition is
  speed, but it's a heavy toolchain (the inverse of brain/00 scope honesty:
  here the complexity *is* paid for by the requirement).
- **Correctness parity between paths is asserted and documented but relies on
  disciplined dual-testing** — the switch enables it; the guarantee is only as
  strong as the suite run against both tiers.

## Transferable lessons

| Lesson | Evidence here | Where it applies / limits |
|---|---|---|
| Detect capability at runtime and dispatch best-first with graceful fall-through; never require the optimal artifact | AVX2→SSE2→C++→Python in fuzz.py | SIMD, GPU/CPU, optional native extensions, model tiers |
| Provide an env-var/config escape hatch to pin the tier for testing and reproduction | RAPIDFUZZ_IMPLEMENTATION | Any auto-dispatching system |
| A fast path and its fallback must return identical results — same function or a bug; test both against one suite | Indel in both paths; api_differences.md | Any accelerated-path-with-fallback design |
| Generate repetitive, correctness-sensitive dispatch boilerplate from a spec | tools/generate_python.py | Wide mechanical surfaces (bindings, dispatchers, adapters) |
| Make a drop-in-replacement promise falsifiable: enumerate every behavioral difference with its reason | api_differences.md | Replacing any incumbent library |
